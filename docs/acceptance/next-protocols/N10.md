四个 DEVICE 项均必须验证 Trojan、VMess、VLESS、Hysteria2，并回归
SOCKS5/AnyTLS/SS2022；覆盖 TCP/UDP、真实 DNS/IPv4/IPv6、平台防递归、
断网/换网、前后台、至少20次连接/停止、HY2跳端口及同步清理。
模拟器、C ABI、容器 IPv6、合成 TUN、历史宿主测试不抵扣这些项目。
所有协议服务端/原站仍须隔离；不自动开放宿主端口或改动工作机 VPN/路由/DNS。

- 本次未发现运行中的 Windows VM；另一虚拟机管理 CLI 超时，未据此认定
  所有离线虚拟机都不存在。原生 Windows 构建转由对应架构 CI 验证。
- 尚未绑定本候选的正式宿主、签名安装记录、Windows10/11设备与Store证据。
  私有宿主身份/路径/配置不进入本仓库或公开 CI。

远端首轮 [36315892710](https://github.com/OneXray/VCore/actions/runs/36315892710)

改用固定字节，避免Windows CRLF导致记录和文件摘要不一致。旧FAIL不改记PASS。

首轮及第二轮 [36316478780](https://github.com/OneXray/VCore/actions/runs/36316478780)
的 Windows ARM64 均在 BoringSSL 原生构建报 LNK1181：Visual Studio 生成器未生成
`.S` 汇编对象，归档却引用 `aes-gcm-avx2-x86_64-apple.obj`。该文件名不代表产物
确为x64；上游统一加入预处理汇编源，由目标宏筛选。上游
[构建说明](https://github.com/google/boringssl/blob/e2a57cfb4d915b4ba820585aef9fdee7bca13fe5/BUILDING.md)
列出了Visual Studio生成器的汇编限制。下一候选使用自有Ninja/LLVM工具链，保持
原生Windows ARM64、MSVC ABI/SDK/static CRT及汇编，不修改第三方或fork。
工具链的小型诊断确认 CL driver 可接受 cmake-rs 的 MSVC 汇编参数并生成ARM64
COFF；GNU driver 拒绝 `-nologo`。这只是工具参数验证，不抵扣原生平台构建。

第二轮 Apple/Android 已通过；Windows x64 已通过生产构建与产物检查，但 C ABI
消费者因 `CreateProcess` 不使用传入环境的 PATH 查找 `cl`，报 WinError 2。
下一候选从 vcvars 环境显式解析编译器绝对路径，并将产物路径绝对化，避免进入
ABI 临时工作目录后丢失 DLL/静态库位置。旧失败保留，不把构建通过扩大为 ABI 通过。
